# PISCIS-I 项目入口

PISCIS 是面向碎片化演奏、旋律即兴与声音探索的掌上数字乐器，采用双手握持、双拇指演奏。当前产品定义以[产品需求文档](运营与开发策略/PISCIS_1.0_PRD_2026-10-20.md)为准；本页只维护项目状态摘要和入口。

## 当前状态

截至 2026-10-20，按工作区资料判断：处于**技术可行性与 MVP 探索阶段**，已有多套子板设计、机械模型和浏览器音色交互原型；这些资料不等同于整机验证完成。

- **主要目标**：收敛可复现的演奏样机链路，明确键盘、主板、音源和结构的集成边界。
- **MVP 范围**：尚未单独冻结，待在当前任务中明确验证切片和通过条件。PRD 第 4 节的 P0 是首代交付范围，摘要为独立演奏、核心交互、EP-1/EO-1、卡片管理、更新救援、可检修结构及基础接口文档；不直接把全部 P0 当成本轮 MVP。
- **关键限制**：主控与资源、供电音频、键盘机械参数和量化验收指标仍有待决项，详见 PRD 第 12、14 节；现有工程分支各有适用范围，不能混用规格。
- **当前开发重点（建议顺序）**：先确认本轮样机采用的工程组合，再处理霍尔键盘稳定触发与对接验证；具体状态只在 [BACKLOG](BACKLOG.md) 更新。

## 日常使用约定

1. **30 秒记下想法**：在 BACKLOG 的 Later 加一行 `- [ ] 想法或问题` 即可，不必分类、编号或先建文档。只把正在推进的少量项放入 Now。
2. **按用途存放**：Goal / Constraint 放 PRD 或相关专题；Task / Issue 放 BACKLOG；Decision 放 DECISIONS；Experiment / Evidence 放 EXPERIMENTS 或已有报告；Specification / Interface 放对应工程规范或代码。专题只串联这些来源。
3. **只维护一份事实**：BOM、接口、PCB、CAD 各以对应版本的源文件为准，入口见工程架构。任务只写动作与链接，README 只留摘要。新任务统一放 BACKLOG；旧工程任务清单保留其版本语境，通过链接查阅，不抄成第二份状态表。
4. **需要时才标状态**：Confirmed = 在注明条件和版本下已验证；Decided = 已决定但可能未验证；Proposed = 候选；Open = 未确定。文件存在、仿真通过、文件级检查和实物验证应分别描述，不能相互替代。不要求每页添加元数据。
5. **需要时才建正式页**：信息反复使用、跨专业共享、成为模块依赖、需要保存重要理由或复现测试、原页明显难维护时才拆分。一次性草稿留在 BACKLOG 或现有相关文件，无需全部整理。
6. **用链接串起交付**：重要问题从任务连到专题，再连需求、接口、实现及证据；D-xxx / E-xxx 只给决策和实验使用，普通任务不强制编号。默认只维护必要的前向链接。
7. **完成后少量收尾**：任务勾选 `[x]` 留在原分区，积累过多时借助 Git 历史清理；没有第四种任务状态。重大取舍补决策，执行过的验证补条件、结果和证据。接口变化检查直接使用方，失效结论保留原证据并标清适用版本。
8. **保持离线可用**：内部链接使用相对路径；本地资料可离线阅读，外部来源仅作延伸参考。相关变更一起纳入对应 Git 仓库；部分子工程有独立 `.git`，根仓库的提交不能替代子工程版本记录，不自动合并仓库或重建工程。

## 何时扩展

| 阶段 | 只在出现实际需求时增加 |
| --- | --- |
| 概念与探索 | 直接使用现有 PRD、调研、BACKLOG、决策；不要求想法全部归档。 |
| 可行性与 MVP | 接口成为依赖时，在对应工程中补正式接口；跨专业问题增多时再加专题。 |
| 工程样机 | 开始多版采购、装配或回归时，明确对应 BOM 的导出规则与版本；对关键需求按需建立 ID 和测试引用，不预建完整追踪矩阵。 |
| 制造与交付 | 真正准备打样/交付时，再增装配说明、测试规范、生产问题及变更记录，绑定实际制造版本。 |

日常维护以推进工程为准，不设强制周报、标签数据库或文档完整性考核。
