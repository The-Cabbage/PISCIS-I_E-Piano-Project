## 1. 推荐阅读路线与基本概念

如果首先想弄清“音源在哪里”，先读 [core/mdaEPiano.h](core/mdaEPiano.h) 的 `VOICE`、`KGRP` 和 `mdaEPiano`，再读 [core/mdaEPiano.cpp](core/mdaEPiano.cpp) 的 `noteOn()` 与 `process()`。采样就在 [core/mdaEPianoData.h](core/mdaEPianoData.h) 的 `epianoData[]` 数组中，不需要另找 WAV 或 SF2。

如果想弄清“一次按键怎么发声”，建议按下面顺序阅读：

```text
src/main.cpp                         板端程序全貌，只有 37 行
src/protocol.h                       电脑与板子交换什么数据
core/mdaEPiano.h                     音源保存哪些状态
core/mdaEPiano.cpp::noteOn           如何建立一个声部
core/mdaEPiano.cpp::process          如何连续算出声音
pc/RemoteEngine.h                   电脑怎样请求这些声音
pc/main_pc_mda.cpp                   谁产生按键、谁消费声音
src/usb_transport.c                  请求与响应怎样穿过 USB
```

先建立以下六个概念，后面函数名会容易理解：

| 概念 | 在本工程中的含义 |
| --- | --- |
| 音符 `note` | MIDI 音符编号，例如 60。这里是编号，不是频率，也不是数组下标 |
| 力度 `velocity` | 0～127；大于 0 触发音符，0 表示松键。普通电脑键盘输入固定为 70 |
| 声部 `VOICE` | 一次发声的播放进度、包络和声道增益。一个音符可以先后触发多个声部 |
| 采样点 | 一个时刻的一个声道幅度；`epianoData[]` 保存单声道素材 |
| 音频帧 | 同一时刻的左右两个输出采样点。本工程每帧 4 字节：左 16 位 + 右 16 位 |
| 音频块 | 一次生成的一组帧。当前一次为 441 帧，在 44,100 Hz 下对应 10 ms |

另外要区分两种“状态”：`notes[60] = 70` 表示电脑认为 60 号键处于按下状态；`voice[v]` 表示板子上某次发声还在继续。按键已经松开，释放尾音仍然可以占用声部。

## 2. 文件职责与编译关系

### 2.1 板端编译什么

[CMakeLists.txt](CMakeLists.txt) 的核心定义是：

```cmake
target_include_directories(app PRIVATE core src)
target_sources(app PRIVATE src/main.cpp src/usb_transport.c core/mdaEPiano.cpp)
```

所以应用自身直接编译三个翻译单元。头文件由 `#include` 展开，不需要再作为 `.cpp` 编译：

```text
src/main.cpp
  ├─ mdaEPiano.h ── config.h
  ├─ protocol.h
  └─ usb_transport.h

src/usb_transport.c
  ├─ protocol.h / usb_transport.h
  └─ Zephyr / CherryUSB 外部头文件

core/mdaEPiano.cpp
  ├─ config.h / mdaEPiano.h
  └─ mdaEPianoData.h ── epianoData[]
```

采样头文件包含在 `mdaEPiano.cpp` 中，编译后采样也进入程序映像；“没有单独的采样文件编译命令”并不表示遗漏了音源。

| 文件 | 阅读时关注什么 |
| --- | --- |
| [src/main.cpp](src/main.cpp) | 音源初始化、请求处理顺序、快照差分、合成和响应打包 |
| [src/protocol.h](src/protocol.h) | 帧数、包长、字节序、CRC 和消息验证 |
| [src/usb_transport.c](src/usb_transport.c) | 描述符、收发回调、消息队列、发送完成信号量 |
| [src/usb_transport.h](src/usb_transport.h) | C/C++ 边界的三个公共函数；`extern "C"` 让 C++ 使用 C 链接名称 |
| [core/mdaEPiano.h](core/mdaEPiano.h) | 参数编号、数据结构、音源类声明 |
| [core/mdaEPiano.cpp](core/mdaEPiano.cpp) | 音符分配、合成算法、控制器和参数计算 |
| [core/mdaEPianoData.h](core/mdaEPianoData.h) | 422,418 个内置 16 位采样值，不必逐行阅读数值 |
| [core/config.h](core/config.h) | 实际使用的采样率、声部容量等，以及大量旧移植配置 |
| [prj.conf](prj.conf) | C++17、浮点上下文、CherryUSB、堆和线程栈配置 |

### 2.2 电脑端编译什么

[build-pc.ps1](build-pc.ps1) 只编译 `pc/main_pc_mda.cpp`，链接 WinMM、窗口绘制、设备枚举和注册表相关 Windows 库。

```text
pc/main_pc_mda.cpp
  └─ RemoteEngine.h
       ├─ AudioEngineInterface.h
       ├─ mdaEPiano.h        使用参数常量等声明
       └─ protocol.h        使用共享消息定义
```

`RemoteEngine` 的函数都在头文件中定义，因此随电脑端入口一起编译。电脑端没有链接 `core/mdaEPiano.cpp`，包含音源头文件也不会让合成算法自动在电脑上运行。

`AudioEngineInterface` 是电脑侧抽象接口；`RemoteEngine` 是它的实现。板端 `mdaEPiano` 本身没有继承这个接口。

## 3. 从系统视角看完整调用链

下面的树中，“调用”表示同一程序内的函数调用；“USB 边界”和“队列边界”表示异步传递，不能当作一条连续的 C++ 调用栈。

```text
电脑 UI 主线程
  Windows 消息分发
    → windowProc(WM_KEYDOWN)
      → synth->noteOn(60, 70)
        → RemoteEngine::noteOn()
          → notes[60] = 70                     此时还没有发送 USB

电脑音频线程，等到有空闲播放缓冲
  → synth->render(left, right, 441)
    → RemoteEngine::render()
      → rt_put16() / rt_put32() / rt_crc()      组装请求
      → RemoteEngine::transfer()
        → WriteFile()
          ── USB 边界 ──>
            CherryUSB 调用 bulk_out()
              → k_msgq_put(request_queue)
                ── 队列边界 ──>
                  mda_usb_request() 中的 k_msgq_get() 返回
                  → 板端 main()
                    → rt_valid_request()
                    → processMidiController(64, pedal)
                    → mdaEPiano::noteOn(60, 70)  建立声部
                    → mdaEPiano::process(right, left, 441)
                      → loopSample()            读素材与循环混合
                      → 包络、混音、滤波、LFO、限幅、量化
                    → rt_put16() / rt_put32() / rt_crc()
                    → mda_usb_send()
                      → usbd_ep_start_write()
                        ── USB 边界 ──>
        → ReadFile() 收满响应
        → rt_valid_response()
      → 解交错到 left[] / right[]
  → 重新交错到 audio.pcm[i][]
  → waveOutWrite()
  → Windows 音频系统和默认播放设备
```

这里有三个节奏：UI 按消息更新状态；音频线程按空闲播放缓冲请求新块；板端收到请求才向前计算 441 帧。代码没有以 `k_msleep(10)` 驱动合成，也没有板端 I2S/DAC 的持续输出任务。

## 4. 板端启动：构造音源和初始化 USB

入口：[src/main.cpp](src/main.cpp) 第 7 行。Zephyr 启动过程进入应用 `main()`；SDK 更底层的启动和驱动实现不在本目录中。

### 4.1 `mdaEPiano engine;` 背后做了什么

构造函数：[core/mdaEPiano.cpp](core/mdaEPiano.cpp) 第 46 行。

```text
板端 main()
  → mdaEPiano::mdaEPiano()
    → new mdaEPianoProgram[NPROGS]{}             分配并清零一个参数槽
    → Fs = SAMPLE_RATE; iFs = 1 / Fs
    → setDecay / setRelease / setHardness / ...
      → setParameter(index, value)
        → programs[0].param[index] = value
        → update()                              计算 DSP 系数
    → setMaxPolyphony(NVOICES)                   单独设置容量，不经过参数数组
    → setLoudness(0.64616)                       单独设置内部音量
    → waves = epianoData                        保存素材地址
    → printf(...)                               打印采样地址及前两个值
    → 填充 kgrp[] 映射表
    → reset_voices()
      → 清包络、活动数、延音和部分滤波/LFO 状态
      → update()
```

构造函数中的 setter 会多次调用 `update()`。这属于初始化阶段，并非每个采样点都这样计算。程序参数数组用了堆分配；声部数组属于对象本身；`epianoData[]` 是静态素材，构造时没有复制整个采样表。

### 4.2 为什么构造后还要再设置参数

构造函数给出通用默认值，`src/main.cpp` 第 9～11 行再覆盖当前原型的声音：

```cpp
engine.setLoudness(1.0f);
engine.setDecay(0.4f);
engine.setRelease(0.3f);
engine.setHardness(0.4f);
engine.setTreble(0.20f);
engine.setPanTremolo(0.5f);
engine.setDetune(0.0f);
engine.setMaxPolyphony(32);
```

所以分析实际声音时，要读完这层覆盖，不能只看构造默认值。

### 4.3 `mda_usb_init()` 的调用链

实现：[src/usb_transport.c](src/usb_transport.c) 第 149 行。

```text
main()
  → mda_usb_init()
    → usbd_desc_register(0, &cdc_descriptor)
    → usbd_cdc_acm_init_intf() × 2
    → usbd_add_interface() × 2
    → usbd_add_endpoint(&out_ep)                 OUT 完成回调为 bulk_out
    → usbd_add_endpoint(&in_ep)                  IN 完成回调为 bulk_in
    → usb_sunxi_otg_base()                      外部 SDK 提供控制器地址
    → usbd_initialize(..., events)              注册设备事件回调
```

这一步是注册函数指针和启动 USB。之后库在相应事件发生时回调这些函数，不是 `mda_usb_init()` 按顺序主动调用所有回调。

## 5. 电脑启动：连接板子和准备播放

入口：[pc/main_pc_mda.cpp](pc/main_pc_mda.cpp) 第 90 行。默认演奏路径先建立板端连接，再打开播放设备和窗口。

### 5.1 `RemoteEngine` 构造函数

```text
电脑 main()
  → std::make_unique<RemoteEngine>()
    → RemoteEngine::RemoteEngine()
      → findPort()
        → SetupDiGetClassDevsW()                获取当前串口设备集合
        → SetupDiEnumDeviceInfo()               逐个枚举
        → SetupDiGetDeviceRegistryPropertyW()   查 Hardware ID
        → 匹配 VID_FFFF&PID_FFFF
        → SetupDiOpenDevRegKey() / RegQueryValueExW()
        → 读取 PortName
        → RegCloseKey() / SetupDiDestroyDeviceInfoList()
        → 要求恰好一个匹配串口
      → CreateFileW()                           独占打开 COM 设备
      → GetCommState() / SetCommState()         配置串口并启用 DTR
      → SetCommTimeouts()
      → SetupComm(); Sleep(200); PurgeComm()
      → render(l, r, 441)                       先做一次实际请求/响应
```

构造时 `notes[]` 全为 0，`sustain=false`，`resetPending=true`。因此第一次请求要求板子清理声部并生成一块没有按键的音频；这块音频只用于建立通信，没有提交给 WinMM 播放。

串口配置写有 `115200`，但板端实际实现的是 USB CDC 数据传输，本目录没有把 PCM 转成 115200 波特物理 UART 的代码，不能用普通 UART 的有效字节率解释这条链路的音频吞吐。

### 5.2 `main()` 后续工作

1. 设置 `synth = &engine`，让窗口代码通过 `AudioEngineInterface*` 使用 `RemoteEngine`。
2. 调用电脑侧 `setVolume()` 和 `setParameter()`。当前实现只是接受预定固定值，不发送参数命令。
3. 创建 `Audio`，准备 44.1 kHz、双声道、16 位 PCM 格式，调用 `waveOutOpen()`。
4. 用 `waveOutPrepareHeader()` 准备四块播放缓冲。
5. 注册窗口类，把 `windowProc` 设为窗口过程，再创建窗口、字体和音区按钮。
6. 创建音频线程，主线程进入 `PeekMessageW → TranslateMessage → DispatchMessageW` 消息循环。

只有第 6 步之后，UI 更新和音频请求才在两个线程中并行进行。`--protocol-test` 会在连接板子之前提前结束；它不经过上述完整启动路径。

## 6. 按下、松开与延音的调用链

### 6.1 按下 A：从窗口消息到远程状态

默认 `baseNote=60`；`keys[]="AWSEDFTGYHUJK"` 按半音排列，所以 A 对应 60，W 对应 61，S 对应 62，依次到 K 对应 72。

```text
DispatchMessageW()
  → windowProc(..., WM_KEYDOWN, 'A', ...)
    → 获取 synthMutex
    → 检查是否系统按键自动重复；重复则忽略
    → 在 keys[] 中找到 i = 0
    → synth->noteOn(baseNote + 0, 70)
      → 虚函数分派到 RemoteEngine::noteOn(60, 70)
        → 检查音符范围，限制力度到 0～127
        → notes[60] = 70
    → down[0] = true
    → InvalidateRect()                          请求重绘键盘
```

`down[]` 用于 UI 本地按键状态；`RemoteEngine::notes[]` 用于下一次通信。两者不是声部数组。`InvalidateRect()` 只请求重绘，绘图分支不会合成音频。

### 6.2 下一次 `render()` 才把按键送出去

```text
音频线程
  → 获取 synthMutex
  → RemoteEngine::render()
    → 将 notes[60] = 70 放入 request[12 + 60]
    → transfer()
      ── USB / 队列边界 ──>
        板端 main()
          → 比较 v=70 与 held[60]=0
          → engine.noteOn(60, 70)
          → held[60] = 70
          → engine.process(..., 441)
```

这里电脑端和板端有两个同名 `noteOn()`：前者写状态，后者创建声部。判断调用到哪个实现，要同时看对象类型和执行进程。

### 6.3 持续按住为什么不会每块重新起音

后续请求仍携带 `notes[60]=70`。板端已有 `held[60]=70`，`v != held[n]` 不成立，便不再调用 `noteOn(60,70)`；原声部继续由 `process()` 推进。

如果持键时把快照力度从 70 改成 80，比较会发现变化，并再次调用 `noteOn(60,80)`。当前实现会重新触发一个声部，不是连续调节已有声部的力度。

### 6.4 松开 A：从状态归零到释放尾音

```text
windowProc(WM_KEYUP, 'A')
  → RemoteEngine::noteOff(60)
    → RemoteEngine::noteOn(60, 0)
      → notes[60] = 0

下一次 render()
  → request[72] = 0
  ── USB / 队列边界 ──>
    板端 main(): held[60] 从 70 变为 0
      → mdaEPiano::noteOn(60, 0)
        → 遍历匹配 note=60 的声部
        → 未踩延音：替换 voice.dec 为释放衰减系数
      → process() 继续输出并逐步减小包络
```

正常松键不立即清除 `activevoices`；尾音需要逐渐衰减到 `SILENCE` 以下，才在音频块结束时被回收。

### 6.5 空格延音

```text
windowProc(WM_KEYDOWN, VK_SPACE)
  → RemoteEngine::sustainPedal(true)
    → sustain = true
  → 下一请求 request[10] = 1
    → 板端 processMidiController(64, 127)
      → sustain = 127 & 0x40                    得到非零状态

这时松开 A
  → mdaEPiano::noteOn(60, 0)
    → 不切换为松键衰减，而把 voice.note 设为 SUSTAIN(128)

松开空格
  → 请求 request[10] = 0
    → processMidiController(64, 0)
      → sustain = 0
      → noteOn(SUSTAIN, 0)
        → 对标记为 128 的声部设置释放系数
```

128 是内部的延音标记，不是一个正常 MIDI 琴键。当前代码会以 128 进入释放系数公式，不会恢复原始音符编号再计算，所以踏板释放与逐键释放的系数路径并不完全相同。

### 6.6 鼠标、切换音区和窗口失焦

| 事件 | 具体调用和行为 |
| --- | --- |
| 鼠标按下 | `windowProc → pianoHit → pianoRect/black`；命中后 `noteOn(baseNote-12+n,70)`，并 `SetCapture()` |
| 鼠标松开或失去捕获 | `noteOff(mouseNote)`，清除 `mouseNote`；松开分支还调用 `ReleaseCapture()` |
| Z/X/C 或音区按钮 | 先 `releaseKeys()`，再把 `baseNote` 改成 48/60/72 |
| 窗口失焦 | `releaseKeys()`，发送本地记录中各按键的松键状态并释放延音 |
| Esc / 关闭窗口 | `DestroyWindow → windowProc(WM_DESTROY) → releaseKeys → running=false → PostQuitMessage` |

`releaseKeys()` 不是 `allNotesOff()`：它逐个释放记录中的键，通常保留正常释放尾音；后者会在下一份请求里设置强制复位标志。

`pianoHit()` 先检查黑键再检查白键，防止黑键被其下方重叠的白键命中区域抢先识别。`pianoRect()` 只负责位置计算，不知道音源状态。

## 7. 请求如何编码、校验与传输

共享实现：[src/protocol.h](src/protocol.h)。协议用显式字节偏移，没有直接把 C/C++ 结构体整块发送，因此不依赖结构体填充和对齐。

### 7.1 请求：144 字节

| 字节偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0～3 | 4 | ASCII `MDRQ` |
| 4～7 | 4 | 请求序号，`uint32_t` 小端 |
| 8～9 | 2 | 帧数，必须等于 `RT_FRAMES=441` |
| 10 | 1 | 延音标志，0 或 1 |
| 11 | 1 | 复位标志，0 或 1 |
| 12～139 | 128 | 音符 0～127 的当前力度；0 为松开 |
| 140～143 | 4 | 前 140 字节的 CRC32，小端 |

### 7.2 响应：1,784 字节

| 字节偏移 | 长度 | 含义 |
| --- | --- | --- |
| 0～3 | 4 | ASCII `MDRS` |
| 4～7 | 4 | 回传本次请求序号 |
| 8～9 | 2 | 帧数 441 |
| 10～11 | 2 | 本块处理后的活动声部数量 |
| 12～15 | 4 | 板端记录的处理耗时，微秒 |
| 16～1779 | 1,764 | 441 帧交错立体声 PCM：`L0 R0 L1 R1 ...` |
| 1780～1783 | 4 | 前 1,780 字节的 CRC32 |

第 n 帧的左声道位于 `16+n*4`，右声道位于 `18+n*4`。有符号 PCM 先按 16 位位模式发送，电脑再转换为 `int16_t`。

### 7.3 七个协议辅助函数

| 函数 | 调用方与作用 |
| --- | --- |
| `rt_put16(p,v)` | 打包方使用，将 16 位整数拆成低字节、高字节 |
| `rt_put32(p,v)` | 打包方使用，将 32 位整数拆成四个小端字节 |
| `rt_u16(p)` | 解析方从两个字节还原 16 位无符号整数 |
| `rt_u32(p)` | 解析方从四个字节还原 32 位无符号整数 |
| `rt_crc(p,n)` | 从全 1 初值开始，逐字节、逐位更新 CRC，使用多项式常量 `0xedb88320`，最后取反 |
| `rt_valid_request(p)` | 校验 magic、441 帧、两个布尔标志及请求 CRC；不检查序号递增，也不逐项校验力度 |
| `rt_valid_response(p,seq)` | 校验 magic、序号等于当前请求、441 帧及响应 CRC |

`RemoteEngine::render()` 先 `++sequence` 再打包；成功后才清除 `resetPending`。`transfer()` 同步写一次请求，循环 `ReadFile()` 直到收满响应，再检查响应有效性。

电脑设置了单次串口超时，并用 `GetTickCount64()+500` 作为读取循环的额外期限；这不是一个可以精确承诺的总通信耗时上限。每次 `ReadFile()` 本身可能阻塞，而且只有返回之后才检查期限。

CRC 检查的是传输数据是否符合校验，不负责固件身份认证。序号匹配用于避免把其他次请求的响应误当本次响应。

## 8. USB 回调、队列和同步

实现：[src/usb_transport.c](src/usb_transport.c)。这里的 IN/OUT 以 USB 主机视角命名：OUT 是电脑发给板子，IN 是板子发给电脑。

### 8.1 描述符回调：回答“这是什么设备”

`cdc_descriptor` 保存五个函数指针。USB 库根据需要调用：

| 回调 | 返回内容 |
| --- | --- |
| `device_descriptor_callback()` | 设备描述符，含 VID/PID |
| `config_descriptor_callback(speed)` | 按 High Speed 或 Full Speed 返回配置描述符 |
| `device_quality_descriptor_callback()` | 设备限定描述符，函数名沿用代码的 `quality` 拼写 |
| `other_speed_config_descriptor_callback(speed)` | 返回另一种速度的配置 |
| `string_descriptor_callback(speed,index)` | 语言、制造商、产品名或序列号；越界返回空指针 |

这部分决定电脑如何枚举设备，与电钢琴波形计算无关。设备采用 CDC ACM，不是标准 USB MIDI 或 USB Audio 类。

### 8.2 `events()`：USB 设备状态变化

```text
USB 库回调 events()
  ├─ CONFIGURED
  │    → ready = true
  │    → usbd_ep_start_read(... rx_buffer, 2048)
  └─ RESET / DISCONNECTED
       → ready = false; dtr_enabled = false
       → assembled = 0
       → k_msgq_purge(request_queue)
```

`ready` 只表示传输层记录的 USB 状态，不等同于当前有音符或电脑正在播放。

### 8.3 `bulk_out()`：把 USB 字节流组装成请求

```text
USB OUT 完成
  → bulk_out(busid, ep, nbytes)
    → 逐字节从 rx_buffer[] 复制到 assembling[]
    → assembled 达到 144 字节
      → k_msgq_put(request_queue, assembling, K_NO_WAIT)
      → assembled = 0
    → usbd_ep_start_read()                      再准备下一次接收
```

`assembled` 是已累计的字节数。USB 一次回调的 `nbytes` 与应用请求长度不是同一个概念；一个请求可以跨回调，一个回调也可以带多个请求。

`K_MSGQ_DEFINE(request_queue, RT_REQUEST, 2, 4)` 创建一个消息大小为 144 字节、容量为 2 的队列，并指定 4 字节对齐。`k_msgq_put()` 复制消息内容，生产者随后可以复用 `assembling[]`。

此回调不验证 CRC，也不按 magic 扫描重同步；它只每 144 字节分一组。队列满时采用不等待提交，返回值未处理，可能丢掉该组请求。正常电脑端一次请求对应一次响应，并不主动连续灌入大量未完成请求。

### 8.4 `mda_usb_request()`：主线程取请求

```text
板端 main()
  → mda_usb_request(request)
    → k_msgq_get(request_queue, request, K_MSEC(100))
      ├─ 取到消息：返回 true
      └─ 超时等失败：返回 false
```

队列把 USB 回调与耗时的合成过程分开。核心 DSP 不在 `bulk_out()` 中执行。回调究竟由中断还是 SDK 工作上下文执行，取决于外部 SDK，不能仅从本目录确认。

### 8.5 `mda_usb_send()` 与 `bulk_in()`：等待发送缓冲可复用

```text
板端 main()
  → mda_usb_send(response, 1784)
    → 检查 ready && dtr_enabled
    → 拷贝到 tx_buffer[]                       当前 1784 < 2048，一次即可
    → k_sem_reset(done_sem)
    → irq_lock()
    → usbd_ep_start_write()
    → irq_unlock()
    → k_sem_take(done_sem, K_SECONDS(1))         等待完成

USB IN 完成
  → bulk_in(..., nbytes)
    ├─ 长度非零且恰好为端点最大包长整数倍
    │    → 追加零长度包；后续完成再给信号量
    └─ 其他情况 → k_sem_give(done_sem)
```

`irq_lock()` 只包围发起发送的短区间，等待完成时已经解锁。信号量把异步回调转成主线程中的同步等待，避免过早改写 USB 尚未发送完的缓冲。

发送完成表示传输层允许复用缓冲，不表示电脑应用已经校验、提交或播放这块声音；那些操作在电脑后续调用链中完成。

`usbd_cdc_acm_set_dtr()` 是提供给 CDC 库的控制回调，更新 `dtr_enabled`；DTR 关闭时清理请求组装进度和队列，但它不直接调用音源。USB 实际何时触发它由 CDC 库决定。

## 9. 板端主循环逐步解读

把 [src/main.cpp](src/main.cpp) 第 13～35 行分成八步，就能读懂控制顺序。

| 步骤 | 代码位置 | 操作和意义 |
| --- | --- | --- |
| 1 | 14～16 行 | 等待请求；100 ms 失败则先释放踏板、停止声部、清空 `held[]`，再继续等待 |
| 2 | 17 行 | `rt_valid_request()` 失败直接跳过，不返回错误响应，也不生成新块 |
| 3 | 18 行 | 请求有复位标志时，释放踏板、停止声部并清空 `held[]` |
| 4 | 19～20 行 | 开始计时，并先应用延音状态 |
| 5 | 21～24 行 | 遍历 128 个音符；力度限制到 127；与 `held[]` 不同才调用 `noteOn()` |
| 6 | 25 行 | `engine.process(right,left,441)` 计算一块声音 |
| 7 | 26～30 行 | 写入响应头、声部数、计时、左右声道交错 PCM 和 CRC |
| 8 | 31～34 行 | 发回电脑；若发送失败则清声部并进入永久等待，需要重启/重新加载恢复 |

有三个容易遗漏的顺序问题：

- **先踏板，后音符变化**：同一快照里既释放踏板又松键时，松键将看到更新后的踏板状态。
- **复位后仍处理当前快照**：如果 `request[11]=1`，但快照里某些力度非零，清理后这些音符还会重新触发。电脑侧 `allNotesOff()` 同时清快照，才实现全部停止。
- **先渲染，再读取声部数**：响应中的 `activevoices` 包含本块末尾回收后的结果，并不等于当前按下琴键数。

计时从应用踏板状态之前开始，在写完部分响应头之后结束；PCM 交错打包、CRC 和 USB 发送在其后。因此该值主要涵盖事件处理与合成，不能当作整条链路延迟。

如果电脑持续发送 CRC 错误但长度正确的消息，队列接收可以成功，程序会在校验处分支跳过；“100 ms 无请求”的保护条件不等于“100 ms 无有效请求”。

## 10. 音源的数据结构

定义集中在 [core/mdaEPiano.h](core/mdaEPiano.h)。先把“固定素材”和“每次演奏状态”分清楚：

```text
epianoData[]                  固定的原始波形素材
  ↑ waves                     音源指向素材的指针

kgrp[]                        固定的采样映射表，描述用素材哪一段
  ↓ noteOn() 查询并复制部分信息
voice[]                       每个正在发声的播放状态
  ↓ process() 每帧更新
left[] / right[]              本次计算出的双声道声音
```

### 10.1 `mdaEPianoProgram`：一套参数

`param[12]` 保存归一化音色参数，当前只分配一个程序槽 `programs[0]`。外部通过 setter 改参数，不能直接访问它的私有数组；`mdaEPiano` 被声明为友元，因此可以访问。

虽然保留了参数编号 8，当前复音限制实际用独立成员 `max_polyphony`，不是从 `param[8]` 计算。

### 10.2 `KGRP`：如何从大数组定位素材

| 字段 | 具体含义 |
| --- | --- |
| `root` | 此键区采样的根音；计算变速播放时，以 `note-root` 得到半音差 |
| `high` | 此键区的上界；还要加上由 Hardness 得到的 `size` 偏移 |
| `pos` | 素材起始数组下标 |
| `end` | 素材段末端位置；触发时声部保存 `end-1` |
| `loop` | 循环回退长度；超过声部末端后从当前位置减去它 |

共有 11 组音高区域，每组对应三个力度项。代码为每组的首项设置 `root/high`，查找时 `k += 3`，所以不会要求另外两个力度项也有 `root/high`。

数组声明为 `kgrp[34]`，实际映射使用 0～32。最高音区有复用同一段素材的力度项，因此“三层结构”也不保证每个高音区都使用三段不同素材。

### 10.3 `VOICE`：一次发声需要记住什么

| 字段 | `noteOn()` 写入什么 | `process()` 如何使用 |
| --- | --- | --- |
| `pos` | 素材起点 | 随相位推进，作为读表下标 |
| `frac` | 0 | 保存采样位置的小数部分，参与线性插值 |
| `delta` | 根据音高和采样率计算的 16.16 增量 | 每输出一帧加到 `frac` 上 |
| `end/loop` | 选中素材的末端和循环长度 | 决定回绕和循环尾部混合 |
| `env` | 力度决定的初始包络幅度 | 乘到采样上，每帧再乘 `dec` |
| `dec` | 自然衰减系数，松键时可以被替换 | 控制包络下降速度 |
| `outl/outr` | 音量和音高声像决定的增益 | 将该声部加入左右混音 |
| `note` | 原始音符编号；延音保持时改为 128 | 松键和踏板释放时寻找对应声部 |
| `f0/f1/ff` | 保留的滤波相关字段 | 当前渲染循环未使用，不代表实际存在逐声部低通滤波 |

`voice[]` 是固定容量数组，当前通常为 32。`activevoices` 表示数组前部有多少项参与渲染；这些项可能处于按下、自然衰减、踏板保持或释放尾音阶段。

### 10.4 跨块持续的全局 DSP 状态

`tl/tr` 是左右声道滤波历史，`lfo0/lfo1` 是 LFO 振荡器历史。这些成员必须跨 `process()` 保留，才不会每块重新起步。每次渲染开始只把当前帧的局部混音 `l/r` 清零，不清空全部声部和滤波历史。

## 11. `noteOn()`：从音符到声部

实现：[core/mdaEPiano.cpp](core/mdaEPiano.cpp) 第 309～374 行。它并不输出 PCM；它准备下一次 `process()` 所需的状态。函数名也包含松键语义：`velocity==0` 进入释放分支。

当前主流程先把音符范围限定在 0～127、把力度限制到 127，再调用它。核心函数本身没有完整的参数范围检查，未来增加直接调用方时应保留这一输入约束。

### 11.1 大于零力度：分配或窃取声部

```text
noteOn(note, velocity > 0)
  ├─ activevoices < max_polyphony
  │    → vl = activevoices
  │    → activevoices++
  │    → 清新声部 f0/f1
  └─ 否则
       → 遍历前 max_polyphony 个声部
       → 选取 env 最小的项作为 vl
       → 覆盖该声部，activevoices 不增加
```

这里采用“较安静者优先”的窃取策略，比较的是包络 `env`，不是实际左右输出瞬时幅度。被覆盖声部不会单独保留尾音或交叉淡出。

### 11.2 计算微调和确定性失谐

```text
k = (note - 60)²
pitchOffset = fine + random × ((k % 13) - 6.5)
如果 note > 60，再加 stretch × k
```

这不是每次 Note On 抽取一个新随机数；同一个音符、同一参数得到相同偏移。当前板端 `Detune=0`，所以 `random=0`；`Tune=0.5` 得到 `fine=0`；`stretch` 固定为 0。

代码复用了局部变量 `k` 和 `l`：前面的 `k` 是音高差平方，后面重新置 0 后变成键区索引；`l` 也先后表示音高偏移、播放步进和增益。阅读时需要按所在代码段重新解释，不能一直当成同一个物理量。

### 11.3 根据 Hardness 找音高键区

```cpp
s = size;
k = 0;
while (note > (kgrp[k].high + s)) k += 3;
pitchOffset += note - kgrp[k].root;
```

`size = int(12*Hardness-6)`。它移动“哪个 MIDI 音符使用哪段采样”的边界，不是直接修改力度阈值。每次跳 3，表示跳过同音高区域的三个力度层。

### 11.4 把半音差换成采样步进

简化变量名后，当前公式等价于：

```text
playbackStep = (32000 / Fs) × exp(0.05776226505 × pitchOffset)
delta = int(65536 × playbackStep)
frac = 0
```

常数约 `0.05776226505 = ln(2)/12`，所以升高 12 个半音，播放速度约乘 2。代码使用 32,000 Hz 作为素材播放速度的基准，再除以当前输出采样率。这里是读表变速，不是为每个音符重新生成一份素材。

### 11.5 根据力度选层并写采样位置

```cpp
if (velocity > 48) k++;
if (velocity > 80) k++;
voice[vl].pos  = kgrp[k].pos;
voice[vl].end  = kgrp[k].end - 1;
voice[vl].loop = kgrp[k].loop;
```

因此 1～48 使用弱层，49～80 使用中层，81～127 使用强层。力度在这里已经改变采样素材，后面还会改变包络幅度。

### 11.6 力度包络与高音补偿

```text
env = (3 + 2*velsens) × (0.0078*velocity)^velsens
若 note > 60，env 再乘 exp(0.01*(60-note))
```

`velsens` 来自 `Velocity Sense`，决定力度曲线。这个 `env` 不要求小于 1；实际输出还会乘素材幅度、声部声道增益和末级增益，最后再限幅。不能看到 `env>1` 就直接认定输出一定削波。

### 11.7 声像与自然衰减

函数记下原始 `voice.note` 后，把用于声像计算的局部音符限制在 12～108：

```text
outr = volume + volume*width*(note-60)
outl = 2*volume - outr
```

以 60 为中心，音符越高越偏向右侧，越低越偏向左侧；宽度由 `Stereo` 控制。这是每个声部建立时计算并保存的增益。

随后将衰减计算用的局部音符下限设为 44，得到：

```text
dec = exp(-iFs × exp(-1 + 0.03*note - 2*Decay))
```

`process()` 每帧做 `env *= dec`。`dec` 越接近 1，下降越慢；增加 Decay 参数会使系数更接近 1，从而延长尾部。

### 11.8 力度为零：释放同音符声部

```text
noteOn(note, 0)
  → 遍历 v < max_polyphony
  → 如果 voice[v].note == note
    ├─ sustain == 0
    │    → dec = exp(-iFs × exp(6 + 0.01*note - 5*Release))
    └─ sustain != 0
         → voice[v].note = 128
```

它不是只查一个声部。若某个音符有多个重复触发留下的声部，这些匹配项会一起进入释放或踏板保持。

Release 是公式参数，不直接以秒保存；系数还依赖音符编号。普通松键不会立即把 `env` 设为 0。

<a id="dsp"></a>

## 12. `process()`：从声部到 PCM

实现：[core/mdaEPiano.cpp](core/mdaEPiano.cpp) 第 224～307 行。它的两个缓冲参数顺序是 **右、左**：

```cpp
void process(int16_t* outputs_r, int16_t* outputs_l, uint32_t numSamples);
```

因此板端的 `engine.process(right,left,RT_FRAMES)` 是有意匹配接口。电脑侧 `render(left,right,frames)` 则先左后右；阅读或替换接口时不能混用。

### 12.1 两层循环决定计算量

```text
process(right, left, 441)
  → 如果帧数为 0，直接返回
  → 每个输出帧 frame = 0..440
    → l = r = 0
    → 每个活动声部 v = 0..activevoices-1
      → 推进相位
      → 循环回绕与边界保护
      → 循环尾部混合 + 相邻点插值
      → 乘包络并推进包络
      → 过载处理
      → 加到 l/r
    → 对 l/r 做公共高频塑形
    → 推进 LFO 并调制左右声道
    → 总增益、限幅、量化
    → 写 outputs_l[frame] / outputs_r[frame]
  → 极小滤波状态归零
  → 回收低于 SILENCE 的声部
```

441 帧、32 活动声部对应最多 14,112 次内层声部处理。这是循环次数推算，不是 CPU 时间测量。即使没有活动声部，外层仍会处理滤波历史、LFO 和输出。

### 12.2 16.16 相位：不必每帧正好走一个素材点

```cpp
V->frac += V->delta;
V->pos  += V->frac >> 16;
V->frac &= 0xFFFF;
```

`delta/65536` 表示“每输出一帧，在原素材中前进多少采样点”。右移 16 位取整数推进量；与 `0xFFFF` 相与保留小数部分。

例如 `delta≈32768` 表示每输出一帧前进约半个素材点，相邻两帧可能读取同一整数位置，但插值小数不同。`delta≈131072` 表示每输出一帧前进约两个素材点。

代码先推进相位，再读采样，因此第一帧并不固定等于素材起点的原始值，而会根据 `delta` 的小数部分做插值。

### 12.3 循环回绕与 50 点混合

当 `pos>end` 时不断减去 `loop`，把读指针移回循环区。随后对位置做数组范围保护。

局部 lambda `loopSample(pos)` 捕获当前 `V` 和音源状态：

```text
distance = (V.end + 1) - pos
若 0 <= distance < 50：
  blend = 1 - 0.02*distance
  sample = int((1-blend)*waves[pos] + blend*waves[pos-loop])
否则：
  sample = waves[pos]
```

越靠近段末端，越多混入与循环起始对应位置的素材，减小回绕处的跳变。它是两个位置的混合，不是混响、合唱，也不是多声部叠加。

这个 lambda 每个声部、每个输出帧调用两次，分别读 `pos` 和 `pos+1`。素材表不被修改；成员 `waves` 虽然用强制转换保留了可写指针类型，但当前渲染只读它。

### 12.4 相邻点插值与幅度归一化

```text
sample0 = loopSample(pos)
sample1 = loopSample(pos+1)
i = sample0 + ((int64(frac)*(sample1-sample0)) >> 16)
x = env * i / 32768
```

可以把它理解成 `sample0 + 小数比例*(sample1-sample0)`，其中小数比例为 `frac/65536`。乘法中间值用 64 位，避免相位小数与采样差值相乘时只用 32 位容纳。

### 12.5 包络、过载和左右声部混音

采样乘完当前 `env` 后，再推进下一帧的包络：

```cpp
V->env *= V->dec;
if (x > 0.0f) {
    x -= od*x*x;
    if (x < -V->env) x = -V->env;
}
l += V->outl*x;
r += V->outr*x;
```

过载只在正半周执行这段二次处理，所以不是简单的对称硬削波。当前 Overdrive 为 0，`od=0`，该非线性减项不改变正半周。

所有声部累加完成后，才进行后续公共处理。`VOICE.f0/f1/ff` 没有参与这条实际渲染路径。

### 12.6 高频塑形

```cpp
tl += tfrq*(l-tl);
tr += tfrq*(r-tr);
l  += treb*(l-tl);
r  += treb*(r-tr);
```

`tl/tr` 是平滑后的低频部分；`l-tl`、`r-tr` 近似提取较高频成分，再用 `treb` 加回或减去。Treble=0.5 得到 `treb=0`，此处不加减高频；当前 Treble=0.2 得到 `treb=-0.84`，会削弱该高频成分。

`tfrq` 在 `update()` 中由指数公式得到。代码使用了 5000/14000 的系数常量，不宜把它们直接当作经过测量的精确截止频率规格。

### 12.7 LFO：颤音与自动声像

```cpp
lfo0 += dlfo*lfo1;
lfo1 -= dlfo*lfo0;
l += l*lmod*lfo1;
r += r*rmod*lfo1;
```

LFO 是低频振荡器，通过相互递推的两个状态持续变化。左右调制同向表现为音量起伏，反向表现为声像左右移动。Pan/Tremolo=0.5 得到 `lmod=rmod=0`，所以当前默认不调制声音，但振荡器仍会继续更新。

### 12.8 输出增益、限幅与量化

```text
l/r 乘 0.5
→ 分别限制到 [-1, 1]
→ 乘 32767
→ 转为 int16_t
→ 右移 REDUCE_LOUDNESS（当前为 0）
→ 写输出缓冲
```

这里包含硬限幅：输入超过范围会被截平。它控制数值输出范围，不是自动响度补偿，也不保证高复音场景没有听感失真。

### 12.9 块结束后的状态维护

若 `tl/tr` 的绝对值极小，将其清零，避免长时间保留极小的浮点状态。然后检查各活动声部，`env<SILENCE=0.0001` 时，把最后一个活动声部复制到空位并减少 `activevoices`。

这个回收操作会改变声部在数组中的位置，声部下标不是长期稳定的音符 ID。当前循环移入新项后继续递增下标，因此被换入项可能留到下一块才重新检查；不能假设每个已静音项都在同一块被完全清除。

以下是按源码公式的教学推演，不是板测输出。假设刚启动、没有其他声部，保持当前板端参数，按下默认音区的 A，即 `note=60, velocity=70`。

| 阶段 | 结果或解释 |
| --- | --- |
| 电脑状态 | `notes[60]=70`，下一请求 `request[72]=70` |
| 板端差分 | 原 `held[60]=0`，调用 `engine.noteOn(60,70)` |
| 声部分配 | 使用 `voice[0]`，`activevoices` 从 0 变成 1 |
| Hardness 偏移 | `int(12*0.4-6)=int(-1.2)=-1`；C++ 向零截断 |
| 音高键区 | 逐组查找，在 `k=12` 停止：根音 60，上界 `63-1=62` |
| 音高偏移 | Tune 居中、Detune 为 0、根音差为 0，最终偏移为 0 |
| 播放步进 | `32000/44100≈0.725624`，`delta≈47554` |
| 力度层 | 70 大于 48、不大于 80，因此从 12 进入 `k=13` |
| 素材范围 | `pos=152864`，声部 `end=173107-1=173106`，`loop=3916` |
| 力度曲线 | Velocity Sense=0.25，所以 `velsens=1.5` |
| 初始包络 | `6*(0.0078*70)^1.5`，约为 2.42 |
| 左右增益 | `volume=1.0*0.16=0.16`；note=60，因此 `outl=outr=0.16` |
| 自然衰减 | 当前参数下为 `exp(-1/44100)`，约 0.9999773 / 帧 |
| 第一输出帧 | 先加相位，小数约 0.7256，在素材起点与下一个点之间插值，然后经过包络和公共 DSP |
| 本次块 | 生成 441 帧，约推进 320 个原素材点；返回电脑后提交播放 |

## 14. 参数 setter、`update()` 与生效时机

### 14.1 两个同名 `setParameter()` 不做同一件事

```text
板端音源
  setTreble(0.2)
    → mdaEPiano::setParameter(MDA_EP_TREBLE, 0.2)
      → 更新 programs[0].param[3]
      → update()
        → 重新计算 treb / tfrq 等 DSP 系数

电脑 RemoteEngine
  setParameter(MDA_EP_TREBLE, 0.2)
    → 发现这是允许的固定组合，直接返回
    → 没有打包参数，没有发送 USB，没有修改板端
```

电脑调用只是现有前端约定的检查。修改电脑调用值通常会抛 `Unsupported parameter`，不会自动改变音色。

### 14.2 12 个参数编号和有效路径

参数编号定义在 [core/mdaEPiano.h](core/mdaEPiano.h) 第 38～50 行；setter 和公式位于 [core/mdaEPiano.cpp](core/mdaEPiano.cpp) 第 157～215 行。

| 编号 | setter / 参数 | 当前板端值 | 主要生效阶段 |
| --- | --- | --- | --- |
| 0 | `setDecay` / Decay | 0.40 | 新 Note On 时计算自然衰减 `dec` |
| 1 | `setRelease` / Release | 0.30 | 后续 Note Off 或踏板释放时计算释放 `dec` |
| 2 | `setHardness` / Hardness | 0.40 | `update` 得到 `size`；新 Note On 选择采样键区 |
| 3 | `setTreble` / Treble | 0.20 | `update` 得到 `treb/tfrq`；后续渲染的公共滤波 |
| 4 | `setPanTremolo` / Pan/Tremolo | 0.50 | `update` 得到 `lmod/rmod`；后续渲染调制 |
| 5 | `setPanLFO` / LFO Rate | 0.65 | `update` 得到 `dlfo`；后续渲染推进 LFO |
| 6 | `setVelocitySense` / Velocity Sense | 0.25 | `update` 得到 `velsens`；新 Note On 计算 `env` |
| 7 | `setStereo` / Stereo | 0.50 | `update` 得到 `width`；新 Note On 计算声像 |
| 8 | Max Poly 编号保留 | 不由参数数组控制 | 通过 `setMaxPolyphony(32)` 设置独立成员 |
| 9 | `setTune` / Tune | 0.50 | `update` 得到 `fine`；新 Note On 计算音高 |
| 10 | `setDetune` / Detune | 0.00 | `update` 得到 `random`；新 Note On 计算失谐 |
| 11 | `setOverdrive` / Overdrive | 0.00 | `update` 得到 `overdrive`；后续 `process` 做非线性处理 |

所有这些浮点参数通常按 0～1 使用，但通用 `setParameter()` 没有索引检查或数值限幅。公开 setter 传入什么，就按公式计算什么，不能把建议范围误解为已实现输入校验。

### 14.3 `update()` 具体更新哪些系数

```text
param[2]  → size = int(12*p-6)
param[3]  → treb = 4*p²-1；选择频率系数并计算 tfrq
param[4]  → lmod/rmod = 2*p-1；根据模式调整右声道符号
param[5]  → dlfo = 6.283*iFs*exp(6.22*p-2.61)
param[6]  → velsens，包含 p<0.25 的分段修正
param[7]  → width = 0.03*p
param[9]  → fine = p-0.5
param[10] → random = 0.077*p²
固定值    → stretch = 0
param[11] → overdrive = 1.8*p
```

Decay/Release 不在这里转换为单一全局 `dec`，因为具体衰减还依赖音符；分别在建立声部和释放声部时计算。

### 14.4 两个特殊 setter

`setLoudness(value)` 只写 `volume=value*0.16`，不经过参数数组，也不调用 `update()`。新声部建立时把这个值复制进 `outl/outr`，所以改变它不会自动重算所有正在播放声部的增益。

`setMaxPolyphony(value)` 把值限制在 1～`NVOICES` 后写 `max_polyphony`。当前函数没有主动裁掉已有声部；如果未来运行中从 32 改成 1，`activevoices` 也不会仅因这个 setter 立即变为 1，需要另外定义清理策略。

## 15. 控制器与复位函数

### 15.1 `processMidiController()` 的分派

实现：[core/mdaEPiano.cpp](core/mdaEPiano.cpp) 第 377 行。函数接受的是 CC 编号和值，不是完整 MIDI 字节流。

| CC 十进制 / 十六进制 | 内部调用或操作 | 当前主流程是否发送 |
| --- | --- | --- |
| 1 / `0x01` | 保存调制轮；达到门限时覆盖 `lmod/rmod` | 否 |
| 64 / `0x40` | 设置 sustain；释放时 `noteOn(128,0)` | 是，每个有效请求应用一次 |
| 66 / `0x42` | 与 CC64 使用同一分支 | 否；没有单独保存严格的 sostenuto 按键集合 |
| 120 / `0x78` | `reset_voices()` | 否 |
| 121 / `0x79` | `reset_controllers()` | 否 |
| 123 / `0x7b` | `stop_voices()` | 否；请求复位在 main 中直接执行相应操作 |
| 126 / `0x7e` | `setMaxPolyphony(1)` | 否 |
| 127 / `0x7f` | `setMaxPolyphony(configuration.max_poly)` | 否 |
| 其他 | 不处理，最后仍返回 true | 不适用 |

CC7 没有实现分支，不能根据头文件提到“主音量”就认为该 CC 可用。返回 true 也不代表每个 CC 都获得了实际支持。

### 15.2 三种“复位”区别很大

| 函数 | 声部 | 延音 | 滤波/LFO 历史 | 参数 |
| --- | --- | --- | --- | --- |
| `reset_voices()` | 清全部 `env`，设初始 `dec`，活动数归零 | 归零 | 清 `tl/tr/lfo0/dlfo`，`lfo1=1` | 保留参数数组，调用 `update()` |
| `stop_voices()` | 清全部 `env`，活动数归零 | 本函数不直接清 | 不直接清历史 | 保留参数数组，调用 `update()` |
| `reset_controllers()` | 不清声部 | 本函数不直接清 | 清部分滤波/LFO 历史 | 调用 `update()`，不是恢复全部音色默认值 |

板端超时和请求复位先调用 `processMidiController(64,0)` 再调用 `stop_voices()`，正是为了同时清理踏板影响。仅调用 `stop_voices()` 不能解释为完整重启了音源；历史滤波状态也可能影响随后几个采样点。

`reset_controllers()` 名称容易让人以为它会清所有控制器，但应以函数体为准。`resume()` 则只重新从固定 `SAMPLE_RATE` 设置 `Fs/iFs` 和 LFO 步进；当前应用入口没有调用它。

### 15.3 未进入主流程的移植代码

`map()` 没有本工程调用方；`set_master_volume()` 是空函数；`master_volume` 没有进入当前实际增益链。`configuration` 全零初始化，当前只在未接入主流程的 CC127 分支读 `max_poly`，其值默认是 0，经过 setter 后会变成 1。

因此不能把这些名字理解为“已接入硬件主音量、EEPROM 配置或复音恢复”。`fillpatch()` 也只保留声明，没有实现和调用；这与完整的预设管理功能不同。

## 16. 电脑播放、线程与对象生命周期

### 16.1 四块播放缓冲怎样循环

实现：[pc/main_pc_mda.cpp](pc/main_pc_mda.cpp) 第 146～167 行的音频线程 lambda。

`Audio` 持有四个 `WAVEHDR` 及四份交错 PCM 数组，每份为 `441*2` 个 `int16_t`。先前的 `waveOutPrepareHeader()` 只准备描述信息，不会自动生成声音或提交播放。

```text
音频线程 while(running)
  → 检查每个 header 的 WHDR_INQUEUE 标志
  → 只处理没有在播放队列中的块
    → 锁住 synthMutex
    → synth->render(left, right, 441)           包含同步 USB 往返
    → 解锁 synthMutex
    → left[j]/right[j] 交错到 pcm[i][2*j/2*j+1]
    → 统计该块左声道的绝对峰值
    → waveOutWrite(device, &header[i], ...)
    → submitted++
  → WaitForSingleObject(audio.ready, 5)
  → 再检查缓冲状态
```

`waveOutWrite()` 提交后，应用不能立刻改写该块；代码通过 `WHDR_INQUEUE` 判断它是否可以复用。播放完成事件会唤醒等待，但事件不直接指出“是哪一块”，所以线程仍重新扫描四个描述头。

启动时四块都空闲，线程可以连续向板子请求并填充四块；之后由播放消费速度形成节奏。它不是每 10 ms 恰好发一次请求的固定定时器，实际请求可能在短时间内成组发生。

四块各覆盖 10 ms，名义排队容量为 40 ms。还有输入采样时刻、已排队音频、USB 往返和系统音频缓冲影响实际响应；不能直接将 10 ms 或 40 ms 写成实测端到端延迟。

### 16.2 为什么先解交错又重新交错

板端响应天然是交错 PCM，`RemoteEngine::render()` 将其拆成 `left[]/right[]`，是为了符合 `AudioEngineInterface::render()` 的双缓冲接口；电脑音频线程再按 WinMM 格式拼成交错数组。

这两次拷贝用于接口适配，没有增加新的合成或效果处理。电脑线程里保留的“master gain”注释也不意味着此处额外乘了音量，实际是直接赋值。

### 16.3 线程和共享状态

| 执行上下文 | 主要状态 | 同步方式 |
| --- | --- | --- |
| 电脑 UI 主线程 | `down/baseNote/mouseNote/pedal`，更新远程按键状态 | 修改 synth 的消息分支使用 `synthMutex` |
| 电脑音频线程 | `RemoteEngine` 收发与响应计数、播放缓冲 | `render()` 期间也持有同一 `synthMutex` |
| 两个电脑线程之间 | `running`、计数及错误标志 | 使用原子变量；音频线程结束后主线程才读取最终非原子连接统计 |
| 板端 main | `engine`、`held`、请求/响应数组 | 同一个主循环顺序处理，当前没有多个线程并发操作 engine |
| 板端 USB 回调与 main | 请求与发送完成状态 | Zephyr 消息队列、信号量，以及传输层状态变量 |

关键影响：音频线程在整个同步 USB 往返期间持锁，UI 输入消息也要拿该锁。独立音频线程可以抵抗 UI 线程自身短暂停顿，但遇到缓慢通信时，UI 输入处理仍可能等待这把锁。不能把“使用了两个线程”解读为所有延迟完全隔离。

`recursive_mutex` 允许同一线程再次取得锁，可容纳窗口 API 引起的嵌套消息处理。具体线程时序和最坏等待时间没有在本文实测。

### 16.4 断流与错误路径

```text
RemoteEngine::transfer()
  └─ 写失败 / 读取失败或超时 / 响应验证失败
       → throw runtime_error
       → 音频线程 catch(...)
       → audioError = 17; running = false

waveOutWrite() 失败
  → audioError = 5; running = false

主线程观察 running=false
  → SetEvent(audio.ready)
  → audioThread.join()
  → 销毁窗口、释放 UI 资源
  → 普通演奏模式显示错误提示
```

`RemoteEngine` 没有自动重新枚举、重开串口和恢复播放的循环。板端发送失败后也会进入停止服务的永久等待分支，需要人工恢复连接或重新加载固件。

`underruns` 的判断是“四块都不在队列里，且之前提交过音频”。这是应用级启发式计数，不能独立证明模拟输出没有爆音、系统级丢帧或其他音频异常。

### 16.5 退出时谁清理什么

```text
主线程结束消息循环
  → running=false
  → SetEvent() 唤醒音频线程
  → join() 等其退出
  → DestroyWindow()（如果仍存在）
  → synth=nullptr；删除字体
  → 局部对象按生命周期逆序销毁
    → Audio::~Audio()
      → waveOutReset()
      → 对已准备 header 执行 waveOutUnprepareHeader()
      → waveOutClose()
      → CloseHandle(ready)
    → unique_ptr 释放 RemoteEngine
      → RemoteEngine::~RemoteEngine()
        → allNotesOff()
        → render(...,441) 尝试将清音状态发送到板端
        → 忽略析构过程中的通信异常
        → 关闭 DTR 和串口句柄
```

析构时请求得到的最后一块声音不会再提交播放。板端 `mdaEPiano::~mdaEPiano()` 负责删除参数数组，但当前板端 `main()` 是无限循环，正常运行不退出该作用域。

### 17.1 板端构建链

```text
build.cmd

```

`prj.conf` 打开 C++17、FPU/FPU sharing、CherryUSB CDC 和对应设备控制器，设置主线程栈 16,384 字节、系统工作队列栈 2,048 字节和堆池 65,536 字节，并关闭 shell、显示和 G2D。

这些配置是软件构建请求，不是实际运行后证明的资源余量。芯片支持代码、`yuzukineko` 板定义、USB 库、链接脚本和工具链依赖外部 SDK；精确版本待补充。

### 17.2 电脑端构建链

```text
build-pc.ps1
  → 临时把指定 g++ 所在目录加入 PATH
  → 编译 pc/main_pc_mda.cpp，包含 core/src/pc
  → 链接 winmm / user32 / gdi32 / setupapi / advapi32
```

### 17.3 RAM 加载链与两个 PowerShell 函数

[tools/load-ram.ps1](tools/load-ram.ps1) 定义了两个辅助函数：`Save-State` 将当前状态保存为 JSON；`Run-Xfel` 调用外部 xfel、保存输出日志、检查退出码并返回日志文本。

```text
load-ram.cmd
  → PowerShell tools/load-ram.ps1
    → 查找恰好一个正常 FEL 设备，检查固件文件存在
    → 创建 output/runs/时间戳/，复制 program.bin，记录映像哈希
    → Save-State
    → Run-Xfel(version)，要求日志匹配 F101
    → Run-Xfel(ddr, f101-s3)                     初始化 PSRAM
    → 写 64 字节探测模式到 0x40000000
    → 从同地址读回，比较文件哈希
    → 写 program.bin 到 0x40000000
    → 按程序长度完整读回，比较哈希
    → Run-Xfel(exec, 0x40000000)
    → 记录 execution_requested
```

脚本在多个步骤更新状态，失败时记录 `failed` 和错误信息，再向外抛异常。`execution_requested` 只表示已请求执行，不代表后续 USB 枚举、音源合成或播放已经验证通过。

这里的 xfel 写入目标是 RAM，脚本未包含 Flash 写入命令；执行 RAM 加载会改变当前板端运行状态，不能把该脚本当成纯只读检查。本文没有运行它。

## 18. 测试分支与调试路线

### 18.1 `--protocol-test` 检查什么

位置：[pc/main_pc_mda.cpp](pc/main_pc_mda.cpp) 第 91～100 行。此分支在连接板子前运行并返回。


退出码 20～24 分别对应上述请求、CRC、响应/序号、响应损坏和键区错误。它不能验证 USB 驱动、板端 DSP、音频播放或实际输入设备。

### 18.2 `--smoke-test` 如何沿主流程运行

此模式仍需要板子、电脑串口和播放设备。它先检查键区，再连接并准备音频，随后按代码时间条件执行：

| 启动后条件 | 脚本化动作 |
| --- | --- |
| 创建音频线程前 | `engine.noteOn(60,70)` |
| 超过约 300 ms | UI 主线程 `Sleep(120)`，模拟 UI 停顿；音频线程继续运行 |
| 超过约 600 ms | `engine.noteOff(60)`，设置 released 标志 |
| 超过约 2,000 ms | 音符 48～79 各写入力度 40，共 32 个 |
| 超过约 6,000 ms | `engine.allNotesOff()` |
| 超过约 10,000 ms | 退出循环，检查统计结果 |

这些是主循环检查条件，不是硬实时调度点。退出成功要求提交块数大于 20、记录峰值大于 0、执行过松键动作、断流计数为 0，并且播放位置计算出的有效速率处于代码给定范围。

测试会发送 32 音符场景，但没有逐个断言 32 个声部均实际发声；松键标志表明调用过 `noteOff()`，没有单独测量尾音是否按期消失。峰值统计只看左声道。阅读测试代码时要把“执行动作”和“验证结果”分开。

[验证状态.json](验证状态.json) 是已有测试摘要，不是本文新生成的结果；其引用原始日志和二进制未在当前目录随附。已有测试范围及其限制见[修改内容对比报告](修改内容对比报告_2026-10-25.md)。

| 观察位置 | 应关注的变量 | 解决的问题 |

### 18.4 按现象排查的短路径

| 现象 | 优先顺序 |
| --- | --- |
| 找不到或打不开串口 | 板端是否运行 → USB 枚举 → VID/PID 匹配数量 → COM 占用 → DTR |
| 连接后响应超时 | `bulk_out` → 队列 → 请求 CRC/长度 → 板端是否已进入发送失败永久等待 |
| 连接正常但没有声音 | 按键快照 → `held` 差分 → `activevoices/env` → PCM 是否非零 → WinMM 输出设备 |
| 持键不断重新起音 | 逐请求检查力度是否变化；当前差分将非零力度变化当作重新 Note On |
| 快速短按偶尔遗漏 | 检查一次完整按下/松开是否都落在两次快照之间 |
| 音高或左右声道异常 | `Fs/delta` → 键区根音 → `process` 的右/左参数顺序 → 协议 PCM 偏移 |
| 改参数无效 | 是否只改了电脑的固定值检查 → 板端是否重编译加载 → 参数是否只对新声部生效 |

## 19. 读代码时容易误解的地方

### 19.1 状态快照不是事件队列

每份请求只记录“现在按着什么”。如果两次请求之间，60 号键经历 `0→70→0`，下一请求仍是 0，板端看不到起音。若已有 70，期间经历 `70→0→70`，最终值仍是 70，板端也看不到重复触发。

当前响应没有样本内事件时间戳，输入只在块前应用。所谓 10 ms 更新是由每块音频时长形成的名义节奏；实际快照间隔还受预填缓冲、锁和通信影响。

### 19.2 名字和注释不能替代函数体

- `update()` 上方写“当前全部禁用”，但下面公式实际执行。
- `processMidiController()` 的头文件说明提到音量，实际没有 CC7。
- `RemoteEngine::isPlaying()` 恒返回 true，不能拿它判断是否有活动声部或是否已断连。
- `getActiveVoices()` 是尾音也在内的声部数，不是按下键数；电脑代理返回最近一次响应缓存的值。
- `reset_controllers()` 没有恢复全部参数默认值；`allNotesOff()` 在电脑侧先改状态，下一次 `render()` 才影响板子。

### 19.3 `config.h` 中存在的宏不等于功能已经接入

它保留 Teensy、LCD、EEPROM、合唱、混响、压缩、SD 卡和 MIDI 端口等旧项目定义。当前实际编译入口没有使用这些模块。

当前 `AUDIO_BLOCK_SAMPLES=256` 只是 `process()` 省略第三个参数时的默认值；实际板端显式传 `RT_FRAMES=441`。同时电脑端又独立定义了 `frames=441`。若改块大小，需要检查协议、电脑播放数组、字节率和测试，而不是只改 config 中的默认值。

采样率同样在核心配置和电脑 `WAVEFORMATEX` 中存在对应设置。修改其中一个不会自动同步另一个。

### 19.4 需要留意的静态代码问题

这些是读源代码时发现的风险，本文没有修复，也没有据此宣称已经在硬件上复现故障：

- `VOICE.note` 等成员没有被构造/复位完整初始化，而松键分支遍历到 `max_polyphony`，可能读到未曾分配过的项；不要把这种写法当作安全初始化范式。
- `muffvel` 未看到初始化，却在 Note On 中参与 `ff` 的计算。虽然当前渲染不使用 `ff`，仍存在读取未初始化成员的问题。
- 采样实际有 422,418 项，宏 `WAVELEN` 沿用 422,414；当前映射末端在其内，但不能假定宏就是完整数组长度。
- 请求组装固定以 144 字节分组，不实现字节错位后的扫描重同步；CRC 失败只丢弃该组。
- 电脑对鼠标和键盘共同按同一音符只做了部分释放保护，没有独立的每音符输入来源计数；扩展输入方式前应检查重叠按键的释放行为。

这些注意项用于理解现状，不改变已确定的技术方案。正式修复时，应另行限定修改范围并设计对应验证。

### 19.5 当前工程在整机中的范围

本工程验证的是“板端计算电钢琴、USB 回传、电脑播放”的局部链路。它尚未提供霍尔键盘采集、板载持续音频输出、显示实体交互、EO-1 或卡片管理。整体产品目标与主控选择仍以[系统架构](../../../engineering/architecture.md)和[现有 PRD](../../../运营与开发策略/PISCIS_1.0_PRD_2026-10-20.md)为准。

### 20.4 三个自测问题

**问题一：按 A 以后，立刻在电脑 `noteOn()` 中查 PCM，为什么找不到？**

因为电脑的 `noteOn()` 只写 `notes[]`。下一次音频线程 `render()` 才将快照送到板端，板端 `noteOn()` 建声部，再由 `process()` 生成 PCM。

**问题二：松键后 `activevoices` 为什么仍为 1？**

松键改变声部的释放系数，声音要继续衰减。直到某个块结束时 `env<SILENCE`，声部才被回收；踩踏板时还会先转为 128 标记等待踏板释放。

**问题三：将 `setTreble()` 改成 0.8，与把电脑 `setParameter(TREBLE,0.8)` 改成 0.8 有什么区别？**

修改板端 setter 调用并重新构建加载，会更新真实音源参数；修改电脑侧调用会触发当前代理的固定值检查，既不会自动修改协议，也不会让板端收到新值。
